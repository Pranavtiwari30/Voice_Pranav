## 6. Projects (detailed)

### 6.1 Conductor: Distributed Job Orchestration Service
**Stack:** Python, PostgreSQL, GitHub Actions | **Type:** Systems / backend engineering

**What it is:** A distributed job orchestration service that runs DAG (directed acyclic graph) workflows across concurrent workers.

**Key engineering ideas:**
- **Exactly-once execution** via PostgreSQL `FOR UPDATE SKIP LOCKED` claiming plus **lease-based crash recovery**, so if a worker dies its job is safely reclaimed.
- **Performance:** sustained **70,955 claims per second** with **zero double-claims**, and **7.01x the throughput** of plain `FOR UPDATE` under contention.
- Implemented scheduling internals **from scratch**: Kahn's topological sort with cycle detection, a min-heap delay queue with O(log n) cancellation, and token-bucket rate limiting.
- **Quality:** 165 property-based and live-PostgreSQL tests at **93% coverage**, gated by a GitHub Actions CI/CD pipeline.

**Why I built it:** I wanted to understand what actually happens underneath tools like Airflow or Celery: how you avoid two workers grabbing the same job, how you recover from crashes, how you rate-limit. Building the internals myself was the best way to learn.

### 6.2 Relay: Event-Driven Integration Platform
**Stack:** FastAPI, React, TypeScript, PostgreSQL | **Type:** Full-stack integration platform

**What it is:** A platform for signed webhook ingestion, declarative data transformation and reliable delivery to external APIs.

**Key engineering ideas:**
- **Transactional outbox** processing with leased claims.
- **Idempotent ingestion**, **bounded retries**, **dead-lettering** and **audited replay**.
- Read-only **MCP-based failure investigations**, so an AI can help diagnose failures without being able to change anything.
- **Quality:** 632 tests and 90% core-logic coverage.

**Why it matters:** It connects directly to my Zensar work on enterprise integration: reliable delivery and replayability are the heart of integration engineering.

### 6.3 Arkive AI: AI Compliance Engine (live in production)
**Stack:** RAG, MongoDB Atlas vector search, REST APIs, Llama Guard 3, Groq, React, Render (backend), Vercel (frontend), CI/CD

**What it is:** A full-stack RAG platform that verifies AI policies against **UNESCO AI Ethics**, **OECD AI Principles** and the **EU AI Act**.

**Key details:**
- Indexed **1,781 document chunks** across **3 governance standards** with semantic vector search through MongoDB Atlas.
- An **8-pillar evaluation pipeline** that returns **exact article citations** and **gap recommendations**.
- **Llama Guard 3** for content moderation and full **audit logging** for end-to-end traceability.
- Black-box and white-box tested each module; CI/CD auto-deploys the backend to Render and the frontend to Vercel on every commit.

**Why I built it:** AI regulation is becoming real, and compliance is a perfect RAG use case because answers must be grounded and cited, not hallucinated.

### 6.4 GPU-Accelerated RAG for Low-Latency LLM Inference
**Stack:** TinyLlama-1.1B, PyTorch, CUDA, FAISS, RTX 4050 | **Type:** Benchmarking / performance engineering

- Benchmarked three pipelines: **Vanilla LLM, CPU RAG and GPU RAG**, over **500 evaluation pairs**.
- GPU RAG reached **1,760 ms latency, 1.56x faster than Vanilla**, driven by a **24x embedding speedup (70 ms to 3 ms)** and batched CUDA inference.
- Showed RAG **reduced hallucination by 33%** (45.0% to 12.0%) with **94.5% answer grounding** on factual queries.
- A **roofline analysis** showed LLM generation, not retrieval, is the compute bottleneck.

**Lesson:** Measure before optimising. The retrieval step I assumed was slow turned out not to be the bottleneck at all.
